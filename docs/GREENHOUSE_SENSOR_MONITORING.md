# پایش دما و رطوبت گلخانه‌ها — آماده‌سازی پیش از خرید سنسور

## هدف
این مرحله، زیرساخت نرم‌افزاری دریافت، ذخیره، نمایش و هشدار دما و رطوبت هر گلخانه را پیش از خرید سخت‌افزار آماده می‌کند. نبود داده نباید با عدد ساختگی یا مقدار پیش‌فرض پنهان شود.

## API پیاده‌سازی‌شده
تمام مسیرها به توکن حساب کاربری نیاز دارند و داده‌ها با شناسه کاربر از یکدیگر جدا هستند:

- `POST /v1/sensors/readings`: دریافت قرائت شامل `greenhouseId`, `sensorId`, `measuredAtEpochMillis`, `temperatureC`, `relativeHumidityPct`, `source` و `idempotencyKey`.
- `GET /v1/sensors/greenhouses/{greenhouse_id}/readings?limit=100`: تاریخچه آخرین قرائت‌ها.
- `PUT /v1/sensors/greenhouses/{greenhouse_id}/thresholds`: تنظیم حداقل/حداکثر دما و رطوبت و مهلت کهنگی داده.
- `GET /v1/sensors/greenhouses/{greenhouse_id}/status`: آخرین وضعیت، زمان دریافت، قدیمی بودن داده و هشدارهای خارج از محدوده.

محدودیت اعتبارسنجی: دما از ‎-20 تا 70 درجه سانتی‌گراد و رطوبت نسبی از 0 تا 100 درصد. زمان بیش از پنج دقیقه در آینده رد می‌شود. کلید idempotency از ثبت دوباره یک پیام جلوگیری می‌کند. تاریخچه به‌صورت رمزگذاری‌شده در پایگاه داده سرور ذخیره می‌شود.

## وضعیت‌هایی که رابط کاربری باید نشان دهد
- `NO_DATA`: هنوز هیچ قرائتی ثبت نشده؛ دما/رطوبت نمایش داده نشود.
- `ONLINE`: داده واقعی دریافت شده و از مهلت تازگی عبور نکرده است.
- `STALE`: آخرین داده قدیمی است و نباید به‌عنوان مقدار زنده نمایش داده شود.
- `SIMULATED`: داده آزمایشی است؛ باید با برچسب واضح «آزمایشی» نمایش داده شود و هرگز داده واقعی تلقی نشود.

هشدارهای دما و رطوبت تنها وقتی تولید می‌شوند که آستانه‌های همان گلخانه تعریف شده باشند. این آستانه‌ها باید با نوع محصول و مرحله رشد تنظیم شوند؛ مقادیر عمومی نباید به‌عنوان توصیه علمی قطعی ارائه شوند.

## آماده‌سازی برای سخت‌افزار آینده
معماری دریافت داده از گیت‌وی محلی پشتیبانی‌پذیر طراحی شده است؛ اما provision امن دستگاه، کلید/گواهی اختصاصی هر گیت‌وی، پروتکل انتخابی (برای نمونه MQTT یا HTTP روی LAN)، کنترل replay، تست قطع‌و‌وصل و کالیبراسیون سنسور هنوز انجام نشده‌اند. توکن حساب کاربری نباید داخل ESP32 یا سخت‌افزار نهایی قرار گیرد. پیش از اتصال واقعی باید هویت دستگاه و مجوز ارسال آن به گلخانه‌های مشخص پیاده‌سازی شود.

## مواردی که هنوز آماده نیستند
- صفحه Android وضعیت و تاریخچه ۴۸ قرائت اخیر را از API می‌خواند و نمودار دما/رطوبت را رسم می‌کند؛ این نسخه تازه در انتظار CI است.
- مدیریت نگاشت دستگاه در Android هنوز ساخته نشده؛ ثبت نگاشت فعلاً از API احراز هویت‌شده انجام می‌شود.
- هیچ سنسور فیزیکی خریداری یا متصل نشده و هیچ داده زنده‌ای اثبات نشده است.
- هشدار push در موبایل و آزمون شبکه محلی هنوز انجام نشده است.

## اتصال ChirpStack

- MQTT topic مورد انتظار: `application/+/device/+/event/up`.
- payload مورد انتظار شامل `deviceInfo.devEui`, `fCnt`, `time`, و `object.temperatureC` / `object.relativeHumidityPct` است.
- پل فقط MQTT روی TLS با CA معتبر را می‌پذیرد و درخواست API را با HMAC-SHA256، timestamp و nonce امضا می‌کند.
- هر DevEUI باید قبلاً با حساب مالک به greenhouse موجود در همان حساب متصل شده باشد.
- secretهای MQTT و HMAC فقط در محیط سرور نگهداری می‌شوند؛ هیچ توکن حساب کاربر در دستگاه LoRaWAN قرار نمی‌گیرد.

## معیار پذیرش نهایی
1. ثبت و نمایش داده سنسور واقعی با شناسه دستگاه معتبر.
2. جداسازی داده بین گلخانه‌ها و حساب‌ها.
3. آزمون idempotency، timestamp، مقادیر خارج از دامنه و داده stale.
4. نمایش تاریخچه و هشدارها در Android.
5. آزمون قطع/وصل Wi-Fi و LAN، ذخیره موقت روی gateway و ارسال مجدد امن.
6. مقایسه سنسور با ابزار مرجع و ثبت کالیبراسیون.
7. تست روی گوشی واقعی و سرور مستقر در شبکه محلی.
