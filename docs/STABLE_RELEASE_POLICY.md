# سیاست نسخه‌بندی و انتشار پایدار Molido Agro AI

## قالب نسخه

نسخه‌های محصول از Semantic Versioning پیروی می‌کنند:

`MAJOR.MINOR.PATCH`

- MAJOR: تغییر ناسازگار در API، داده یا رفتار عمومی محصول.
- MINOR: قابلیت جدید با حفظ سازگاری قبلی.
- PATCH: رفع اشکال و اصلاحات سازگار.

## خط نسخه فعلی

- نسخه پایه توسعه: `0.1.0`
- نسخه‌های ساخت CI: `0.1.0-dev.<run_number>`
- نسخه پایدار عمومی: هنوز تعیین/منتشر نشده است.
- اولین نسخه `1.0.0` تنها پس از عبور از معیارهای پذیرش پایدار مجاز است.

## قواعد Android

- `versionName` از `version.properties` خوانده می‌شود؛ Tag معتبر انتشار مقدار نسخه را override می‌کند.
- ساخت‌های غیر Tag در CI پسوند `-dev.<run_number>` می‌گیرند تا با انتشار پایدار اشتباه نشوند.
- `versionCode` در CI از شماره اجرای GitHub Actions گرفته می‌شود و برای ساخت محلی از مقدار پایه فایل نسخه استفاده می‌کند.
- همه APKهای انتشار باید با همان کلید ثابت پروژه امضا شوند؛ تعویض کلید بدون برنامه مهاجرت ممنوع است.
- تأیید V2/V3، یک signer، fingerprint مورد انتظار و SHA-256 فایل بخشی از gate انتشار است.

## انتشار

1. تغییرات فقط از PR بررسی‌شده وارد شاخه اصلی شوند.
2. تست‌های API، Docker، Android unit و instrumentation همگی موفق باشند.
3. نصب تازه و ارتقای نسخه قبلی روی دستگاه Android واقعی آزموده شوند.
4. بازیابی backup و سناریوهای sync چنددستگاهی آزموده شوند.
5. اتصال Gateway/سنسورها فقط پس از آزمون سخت‌افزار واقعی تأیید شود؛ در غیر این صورت باید صریحاً خارج از محدوده انتشار اعلام شود.
6. امنیت، حریم خصوصی، مجوزها، مهاجرت دیتابیس و سازگاری نسخه‌ها بازبینی شوند.
7. پس از تأیید Release Manager، Tag پایدار `vMAJOR.MINOR.PATCH` ایجاد شود.
8. انتشار خودکار فقط پس از موفقیت تمام Jobهای لازم انجام شود و APK، manifest، checksum و release notes را شامل شود.

## ممنوعیت ادعای نادرست

- APK ساخته‌شده در CI، نسخه منتشرشده محسوب نمی‌شود.
- تست Emulator جایگزین تست گوشی واقعی نیست.
- وجود کد اتصال سنسور به معنی اتصال فیزیکی Gateway نیست.
- موفقیت API به معنی استقرار و بازیابی عملیاتی سرور نیست.
- قابلیت ناقص یا آزمایش‌نشده نباید Stable یا Production-ready نامیده شود.
