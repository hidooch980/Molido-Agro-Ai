# استقرار محلی LAN، TLS و پشتیبان‌گیری

این راهنما برای استقرار self-hosted در شبکه داخلی گلخانه است. قبل از نصب، یک نام DNS داخلی ثابت مانند `agro.home.arpa` انتخاب و آن را به IP ثابت سرور LAN متصل کنید. این نام نمونه است و نباید بدون تنظیم DNS در APK ثبت شود.

## توپولوژی پیشنهادی

- Android و سرور API فقط از طریق HTTPS به Caddy متصل شوند.
- API روی شبکه Docker داخلی بماند و پورت 8080 آن روی LAN منتشر نشود.
- Caddy تنها ورودی LAN روی TCP/443 باشد.
- پایگاه SQLite در volume پایدار `/data` نگهداری شود.
- ChirpStack و MQTT broker روی شبکه خصوصی؛ MQTT با TLS، کاربر اختصاصی و ACL محدود به topicهای uplink اجرا شود.
- پل MQTT فقط به broker و endpoint داخلی HTTPS دسترسی داشته باشد.

## TLS داخلی

برای شبکه‌ای بدون دامنه عمومی، Caddy می‌تواند CA داخلی بسازد. نمونه Caddyfile:

```caddyfile
agro.home.arpa {
    tls internal
    reverse_proxy api:8080
}
```

گواهی ریشه CA مربوط به Caddy باید از مسیر امن به دستگاه‌های Android مورد اعتماد نصب شود. فایل CA خصوصی را هرگز در APK، GitHub یا پیام‌رسان قرار ندهید. در محیط تولید سازمانی بهتر است از CA داخلی مدیریت‌شده استفاده شود. از HTTP cleartext یا غیرفعال کردن اعتبارسنجی TLS در اپ استفاده نکنید.

نکته مهم Android 7+: اپ تنها CAهای مخزن سیستم را باور می‌کند؛ نصب CA به‌عنوان «CA کاربر» برای نسخه release کافی نیست. پیکربندی `app/src/main/res/xml/network_security_config.xml` چنین است:

- نسخه release فقط `system` را باور می‌کند و cleartext را ممنوع می‌کند.
- نسخه debug با `debug-overrides` علاوه بر `system`، `user` را هم می‌پذیرد؛ پس آزمون LAN با CA خصوصی Caddy فقط با build نوع debug ممکن است.

برای نسخه release یکی از دو مسیر لازم است: گواهی معتبر عمومی (مثلاً Let's Encrypt با چالش DNS روی دامنه واقعی) یا نصب CA داخلی در مخزن سیستم دستگاه‌ها با MDM/root. قرار دادن CA خصوصی داخل APK یا غیرفعال کردن اعتبارسنجی TLS مجاز نیست.

## متغیرهای محرمانه

مقادیر زیر فقط در فایل محیطی خارج از مخزن یا secret manager سرور قرار گیرند؛ فایل حاوی اسرار را commit نکنید:

- `MOLIDO_JWT_SECRET`: حداقل ۳۲ بایت تصادفی.
- `MOLIDO_DATA_KEY`: کلید ۳۲ بایتی Base64 برای رمزگذاری payloadها؛ از دست رفتن آن به معنی از دست رفتن امکان رمزگشایی داده‌های ذخیره‌شده است.
- `MOLIDO_CHIRPSTACK_INGEST_SECRET`: راز مستقل با حداقل ۳۲ کاراکتر برای امضای HMAC پل MQTT.
- `CHIRPSTACK_MQTT_USERNAME` و `CHIRPSTACK_MQTT_PASSWORD`: حساب اختصاصی با دسترسی فقط subscribe به topicهای لازم.
- `CHIRPSTACK_MQTT_CA_CERT`: مسیر CA صادرکننده گواهی broker.
- `MOLIDO_API_CA_CERT`: در صورت نیاز مسیر CA صادرکننده گواهی HTTPS API.
- `MOLIDO_TRUST_PROXY_HEADERS`: فقط وقتی Caddy تنها مسیر دسترسی به API است روی `1` تنظیم شود تا محدودیت نرخ از `X-Forwarded-For` استفاده کند؛ در غیر این صورت مقدار `0` بماند.

برای Android، مقدار `SYNC_BASE_URL` در build باید URL نهایی HTTPS LAN باشد. چون hostname و CA محیط نصب هنوز تعیین نشده‌اند، نباید URL فرضی را در نسخه انتشار قرار داد.

## پشتیبان‌گیری

1. زمان‌بندی پشتیبان‌گیری روزانه و پیش از هر ارتقا تنظیم شود.
2. از SQLite با روش online backup یا پس از توقف سرویس، snapshot سازگار تهیه شود؛ کپی ساده فایل فعال DB بدون تضمین سازگاری توصیه نمی‌شود.
3. فایل پشتیبان با کلیدی مستقل از `MOLIDO_DATA_KEY` رمزگذاری و خارج از دستگاه سرور نگهداری شود.
4. حداقل یک نسخه آفلاین و یک نسخه چرخشی نگه دارید؛ دسترسی فایل‌ها محدود و ثبت‌شده باشد.
5. هر ماه بازیابی آزمایشی روی ماشین جداگانه و بررسی `PRAGMA integrity_check` انجام شود.
6. کلیدهای رمزگذاری و امضای بکاپ باید جداگانه و امن نگهداری شوند؛ بکاپ بدون کلید بازیابی معتبر نیست.

نمونه اجرای پشتیبان‌گیری از داخل محیط سرور (کلید بکاپ مستقل و ۳۲ بایتی Base64 لازم است):

\`\`\`bash
export MOLIDO_BACKUP_KEY='BASE64_32_BYTE_BACKUP_KEY'
python server/backup_db.py /secure-backups/molido-$(date -u +%Y%m%dT%H%M%SZ).sqlite3.enc
\`\`\`

کلید نمونه بالا placeholder است و نباید عیناً استفاده شود. کلید واقعی را از مولد امن تولید و جدا از فایل backup نگهداری کنید.

## بازیابی

- ابتدا سرویس API و پل MQTT متوقف شوند.
- با `MOLIDO_BACKUP_KEY` صحیح، اسکریپت `python server/restore_db.py /secure-backups/backup.sqlite3.enc` اجرا شود؛ اسکریپت قبل از جایگزینی، احراز اصالت AES-GCM و integrity check را انجام می‌دهد.
- آخرین backup رمزگشایی‌شده در مسیر staging قرار گیرد.
- قبل از جایگزینی دیتابیس فعال، `PRAGMA integrity_check` باید `ok` برگرداند.
- فایل فعال به‌صورت اتمیک جایگزین و مالکیت/مجوزهای فایل بررسی شود.
- API راه‌اندازی و health، ورود کاربر، sync و history سنسورها بررسی شوند.
- پس از اطمینان، پل MQTT دوباره فعال شود تا uplinkها وارد شوند.
- بازیابی باید در محیط آزمایشی و پیش از پذیرش production تمرین شود.

## معیار پذیرش استقرار

- DNS داخلی از گوشی و سرور resolve شود.
- TLS chain روی Android معتبر باشد و hostname match شود.
- API از LAN فقط از طریق reverse proxy در دسترس باشد.
- پورت MQTT عمومی نباشد؛ TLS و ACL محدود اعمال شوند.
- mapping دستگاه به گلخانه و ارسال uplink امضاشده تست شود.
- restart سرور داده‌ها را حفظ کند.
- restore backup روی یک محیط جداگانه موفق شود.
- تست قطع و وصل LAN و صف/ارسال مجدد gateway انجام شود.

## اتصال اپ به سرور

اپ منتشرشده هیچ آدرسی از پیش ندارد، بنابراین تا وقتی سرور معرفی نشود ثبت‌نام و ورود انجام نمی‌شود (پیام «سروری تنظیم نشده است»). مراحل:

1. سرور را با `docker compose up -d` یا `uvicorn app.main:app` روی سرور یا رایانه خود اجرا کنید.
2. در اپ، بخش «اتصال به سرور همگام‌سازی» را باز کنید و آدرس را وارد کنید؛ مثلاً `molido.example.com` (به‌طور خودکار `https://` اضافه می‌شود) یا برای آزمایش روی همان دستگاه `http://127.0.0.1:8000`.
3. «ذخیره آدرس» را بزنید؛ سپس «ساخت حساب» یا «ورود».
4. برای شبکه داخلی بدون گواهی معتبر، از http فقط روی loopback استفاده کنید؛ برای LAN واقعی TLS با hostname معتبر لازم است.

اگر اصلاً سرور نمی‌خواهید، دکمه «شروع بدون سرور» یک پروفایل محلی (`local-<uuid>`) می‌سازد؛ همان داده‌های دستگاه را نگه می‌دارد، همگام‌سازی را غیرفعال می‌کند و بعد از خروج با همان دکمه دوباره فعال می‌شود.

آدرس در SharedPreferences (`molido_server_config`) ذخیره می‌شود و ورود/همگام‌سازی/سنسورها همگی از آن استفاده می‌کنند. با «پاک کردن»، اپ به حالت فقط‌محلی برمی‌گردد و داده‌های موجود حذف نمی‌شوند.

## وضعیت فعلی

این سند طرح استقرار و معیار پذیرش است، نه گزارش نصب واقعی. hostname، گواهی TLS، secrets عملیاتی، broker، gateway و سنسورهای فیزیکی هنوز در محیط کاربر تنظیم یا آزمایش نشده‌اند.
